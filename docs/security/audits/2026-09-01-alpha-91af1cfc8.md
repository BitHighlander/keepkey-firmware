# Alpha audit findings 2026-09-01 (alpha@91af1cfc8)

## [P1] thorchain — MsgDeposit amount screen blanks out (unchecked bn_format_uint64) while the real amount is signed
- **dimension**: display-vs-signed
- **file**: lib/firmware/fsm_msg_thorchain.h
- **line**: 210
- **description**: In the deposit branch of fsm_msgThorchainMsgAck, amount_str[32] is formatted with bn_format_uint64(depmsg->amount, NULL, asset_str, 8, 0, false, amount_str, sizeof(amount_str)) and the return value is ignored. asset_str is " "+asset, up to a 20-byte suffix (protobuf caps ThorchainMsgDeposit.asset at max_size 20, i.e. 19 chars). bn_format writes from the end of the buffer: null(1) + suffix(<=20) + the rendered number. When suffix + rendered number exceeds 31 bytes, bn_format hits its BN_FORMAT_ADD_OUTPUT_CHAR overflow guard, executes memset(output,'\0',output_length) and returns 0, leaving amount_str as an empty C string. The code does not check this (unlike the send branch at line 168, which aborts on a false return with 'Failed to format amount'). confirm_transaction_output then renders "Send  to\n<signer>" with no amount and no asset, yet thorchain_signTxUpdateMsgDeposit still commits the true depmsg->amount into the SHA256 that is signed. The amount -- a signed field -- is entirely hidden from the user.
- **exploit**: A malicious/compromised host sends a THORChain MsgDeposit with a typical long asset identifier (e.g. asset="ETH.USDT-0XDAC17F9", 19 chars -> 20-byte suffix) and any amount whose 8-decimal rendering exceeds ~11 characters, e.g. amount=123412345678 base units (renders "1234.12345678", 13 chars): 20+13+1 = 34 > 32, so bn_format returns 0 and zeroes amount_str. The device shows 'Send  to <thor-signer>' -- no number at all -- and if the user approves, the device signs a deposit of the full attacker-chosen amount that was never displayed. Round amounts (trailing zeros stripped) fit and display correctly, so the defect passes casual testing while firing on ordinary fractional real-world amounts.
- **remediation**: Check the return value of bn_format_uint64 in the deposit branch exactly as the send branch does: on a 0/false return, call thorchain_signAbort(), fsm_sendFailure(FailureType_Failure_FirmwareError, "Failed to format amount"), layoutHome() and return. Additionally size amount_str to hold the worst case (20-digit uint64 + '.' + 8 fractional + 20-byte suffix + NUL, ~50 bytes) or drop the asset suffix and confirm the asset on its own screen as the send path does with the denom.
- **confidence**: high

## [P1] solana — Certified/schema flow clear-signs force_opaque instructions (unchecked SPL transfer/approve/set-authority) through inadequate screens with no blind-sign warning
- **dimension**: display-vs-signed
- **file**: lib/firmware/solana.c
- **line**: 982
- **description**: The parser signals "this instruction is unsafe to clear-sign" only through the single transaction-level bool force_opaque (solana.c:161,222,249,313,345,355,374). Several RECOGNIZED instruction types set it: unchecked TOKEN_TRANSFER (313), unchecked TOKEN_APPROVE (355), TOKEN_SET_AUTHORITY (374), SYSTEM_CREATE_ACCOUNT (249). Their per-instruction record keeps type != SOL_INSTR_UNKNOWN and external == false. solana_schemaApplies() (solana.c:982-988) and the certified branch (fsm_msg_solana.h:886) accept every non-schema instruction as long as it is NOT SOL_INSTR_UNKNOWN and NOT external — they never consult force_opaque, which was lost the moment it collapsed into the tx-level flag. So a certified schema transaction may legally carry an unchecked SPL Token Transfer alongside the schema-described instruction. solana_confirmSchemaTransaction() then renders that transfer via solana_confirmInstruction()'s SOL_INSTR_TOKEN_TRANSFER branch (fsm_msg_solana.h:171-214): has_mint is false so NO mint screen is shown, and extra_u8 is 0 so solana_formatTokenAmount() prints the raw base units at 0 decimals ("Send 1000000 tokens to X" for 1 USDC). The certified path ends with a plain "Sign this Solana transaction?" (fsm_msg_solana.h:1103) and emits NO blind-sign / "cannot verify" warning, so the intentional AdvancedMode blind-sign gate that unchecked transfers are supposed to hit is entirely bypassed. The same gap exposes TOKEN_SET_AUTHORITY (account takeover shown as a bare "Set token authority to X") and SYSTEM_CREATE_ACCOUNT (owner/space hidden).
- **exploit**: Certified schemas are reusable and travel with transactions (design: one attestation per program+discriminator, replayed by every later tx); the delegate signs only the schema, never the transaction. A malicious host takes any legitimate certified schema payload+signature+certificate it has observed, builds a legacy/v0 message containing (1) the schema's UNKNOWN instruction and (2) an unchecked SPL Token Transfer (opcode 3) moving the victim's USDC to the attacker with the victim as authority. solana_schemaApplies passes (transfer is non-UNKNOWN, non-external), certified=true, tx_review=OPAQUE. The device shows the schema instruction, then "Send 1000000 tokens to <attacker>" (no mint, wrong scale), then "Sign this Solana transaction?" with no warning. The victim is a required signer so solana_signerInTx passes. Attacker drains the token balance; no delegate secret is needed.
- **remediation**: Track per-instruction clear-sign safety: give SolanaParsedInstruction a flag set false whenever the parser would force_opaque for THAT instruction (unchecked transfer/approve, set_authority, create_account, token-2022 checked, external). Require solana_schemaApplies() and the certified branch to reject any non-schema instruction that is not clear-sign-safe — i.e. only permit "other" instructions whose type would independently classify the tx as VERIFIED — rather than merely rejecting SOL_INSTR_UNKNOWN/external. Alternatively refuse any schema/certified transaction in which the parser raised force_opaque for a reason other than the single schema-explained UNKNOWN instruction.
- **confidence**: high

## [P1] ethereum-contracts — MakerDAO OTC-provider confirmation is inverted (missing '!'): a user's rejection is signed as approval, and the OTC address can be hidden entirely
- **dimension**: display-vs-signed
- **file**: lib/firmware/ethereum_contracts/makerdao.c
- **line**: 299
- **description**: In makerdao_confirmClose (line 299) and makerdao_confirmWipe (line 565) the OTC-provider check reads `if (confirmParamIsOTCProvider(...)) return false;` -- the logical negation is missing. The sibling makerdao_confirmWipeAndFree (line 615) has the correct `if (!confirmParamIsOTCProvider(...)) return false;`. confirmParamIsOTCProvider returns the user's confirm() choice (true = approved) in the non-OasisDEX branch, and returns false early when the ABI word's high 12 bytes are non-zero. With the inverted sense: (a) when the user REJECTS the 'Confirm OTC: 0x...' screen it returns false, the `return false` is skipped, and the transaction proceeds to sign shut()/wipe() WITH that OTC provider -- consent inversion; (b) a host that sets the high 12 bytes of the OTC word non-zero forces an early false return, so the OTC screen is skipped entirely and the final screen shows only 'Close CDP N?' while the router still casts the low 20 bytes to the OTC address and executes against it -- a signed field never shown; (c) a legitimate OasisDEX OTC returns true and is refused (DoS). confirmWipe compounds this by reading getParam(msg,2) (the wad/DAI amount word) instead of getParam(msg,3) where the 4-arg wipe(address,bytes32,uint256,address) OTC address actually lives, so the real OTC provider is never validated or displayed regardless.
- **exploit**: Malicious/compromised host builds shut(tub, cup, otcProvider) to the SaiProxy with the OTC ABI word encoded as 0x0000...01 || <attacker20bytes> (non-zero high byte). confirmParamIsOTCProvider returns false immediately, the inverted guard skips its refusal, and the device signs a close routed through the attacker's OTC contract while displaying only 'Close CDP N?'. Alternatively, present a benign-looking OTC screen; the user presses reject, and the transaction is signed anyway.
- **remediation**: Restore the negation to match confirmWipeAndFree: `if (!confirmParamIsOTCProvider(...)) return false;` in both confirmClose and confirmWipe, and fix confirmWipe to read getParam(msg,3) (the 4-arg OTC address) rather than getParam(msg,2). Add a regression test that a rejected OTC screen aborts signing and that a non-canonically-encoded OTC address is still displayed or refused.
- **confidence**: high

## [P2] osmosis — sender committed to signature but never displayed, validated, or escaped (LP-Add/Remove, Swap, IBC-Transfer)
- **dimension**: display-vs-signed
- **file**: lib/firmware/osmosis.c
- **line**: 653
- **description**: In osmosis_signTxUpdateMsgIBCTransfer (line 653), osmosis_signTxUpdateMsgSwap (line 714), osmosis_signTxUpdateMsgLPAdd (line 451) and osmosis_signTxUpdateMsgLPRemove (line 505), the host-supplied `sender` string is interpolated into the amino sign-doc via a plain `%s` (e.g. `"sender":"%s"`). Unlike MsgSend (which derives from_address from the node) and unlike chain_id/memo/validator_address (which are passed through tendermint_sha256UpdateEscaped), `sender` is: (1) never rendered on any confirm screen for these four message types (LP-Add shows only Max Deposit A/B, Pool ID, Share Out; Swap shows only Swap Input, Minimum Output, Pool ID; IBC shows only amount, receiver, channel, port, revision height/number); (2) never bech32-validated in the fsm handler (only has_sender is checked); (3) never escaped. In IBC-Transfer the handler even derives the device's own from_address via tendermint_getAddress and then discards it, signing the host's `sender` instead. This violates the invariant that every byte affecting the signature must be disclosed: the account whose funds move is a signed field the user never sees, and because it is unescaped it is a JSON-injection surface into the signed document.
- **exploit**: A malicious/compromised host sends an OsmosisMsgAck for a swap or IBC transfer with a `sender` the user never approves; the device signs it with no on-screen disclosure of the acting account. The unescaped path additionally lets `sender` carry `"` and arbitrary bytes (e.g. osmo1self...","k":"v) that are hashed into the signature verbatim, undisclosed. Practical fund-redirection is bounded because a Cosmos sign-doc is only accepted when sender matches the signing pubkey and injected/duplicate keys break canonical amino JSON, so this is a disclosure + fail-open-parsing gap rather than direct theft, but it breaks the see-what-you-sign guarantee and the file's own stated escaping policy.
- **remediation**: Bind `sender` to the device by deriving it from the node (as MsgSend does with from_address) and rejecting any mismatch, or at minimum bech32_decode/validate `sender` against the osmo/tosmo HRP, route it through tendermint_sha256UpdateEscaped instead of %s, and add a confirm_osmosis_address("Confirm Sender", sender) screen so the signed acting account is disclosed for LP-Add, LP-Remove, Swap, and IBC-Transfer.
- **confidence**: high

## [P2] eos — Asset symbol accepts a NUL byte followed by non-zero bytes; on-screen token symbol is truncated at the NUL while the full symbol is signed
- **dimension**: display-vs-signed
- **file**: lib/firmware/eos.c
- **line**: 185
- **description**: eos_formatAsset validates each of the 7 symbol bytes with `if (!('A' <= c && c <= 'Z') && c != 0) return false;` (lines 186-190) and then unconditionally writes every byte, including embedded zeros, into the display string via `*s++ = c` (line 191). The check accepts a non-canonical symbol where a zero byte is followed by non-zero letters (e.g. bytes 'A',0,'B'), so an interior NUL is written into the asset string. Every action confirm renders the asset with printf "%s" (Transfer, Delegate, BuyRam, etc.), which stops at the first NUL — the user sees only the prefix before the embedded zero. eos_compileAsset (eos.c:214) hashes the full raw 8-byte symbol into the signed preimage, so the signature commits to symbol bytes the screen never showed.
- **exploit**: A host submits an eosio.token transfer whose quantity symbol bytes are 'A',0,'X','X','X',0,0 with precision 4. The device displays "Transfer 1.0000 A from ... to ...?"; the user, believing they are moving token 'A', approves. The signed action commits to a different token symbol ("A\0XXX") than the one disclosed, breaking the see-exactly-what-you-sign invariant on the field that identifies which token leaves the account.
- **remediation**: Enforce canonical symbols: once a zero byte is seen, require all remaining higher bytes to also be zero (reject any non-zero byte after a zero), and stop writing the display string at the first zero. Reject otherwise.
- **confidence**: medium

## [P2] confirm-display — page_body_confirm() caps at 100 pages and returns approval instead of refusing when the body needs more
- **dimension**: dead-surface
- **file**: lib/board/confirm_sm.c
- **line**: 478
- **description**: In page_body_confirm() the counting pass caps the page total: `if (pages > 99) break;` leaves `pages == 100` even when the body would require more screens. The render loop then iterates `for (page = 0; page < pages && *p; page++)` and, on the 100th page, evaluates `last = (page + 1 == pages)` as true and sets `ok = true`, returning approval while `*p` still points at un-rendered body bytes. Every other completeness guard in this file fails CLOSED on the same situation: confirm_constant_power_subpage_take() returns 0 so the pager refuses (line 698), confirm_bytes() does `goto cleanup` with approved=false when a page cannot be formed (app_confirm.c:471/480), and confirm_constant_power_paged() breaks with ok=false when take==0 (line 745). page_body_confirm() alone drops the remainder and reports success, which is exactly the 'field-count cap that drops the remainder without refusing' pattern the audit targets: the tail of request_body is committed to the signature (or written to the message being approved) but never shown, and the caller sees a true return.
- **exploit**: A host supplies a body (<= BODY_CHAR_MAX-1 = 351 chars, e.g. a message-sign / cipher / identity field that reaches confirm() via the standard layout) laid out so the renderer needs more than 100 screens - achievable with newline-dense content, since each standard page holds only ~3-4 rows, so ~350 newline/short-row bytes exceed the 99 cap. Counting stops at pages=100; the render loop draws 100 pages, marks the 100th 'last', sets ok=true, and returns approval. The bytes after the 100th page were part of the approved/signed body but were never displayed, and no 'Cut Off' or paging indicator fired. The practical hidden span is bounded by the 352-byte strbuf, so the concealable tail is small, but the function returns consent for content the user never saw rather than refusing.
- **remediation**: Make the cap fail closed: when the pass-1 counter hits the limit (body needs more pages than MAX_PAGES), return false from page_body_confirm() (refuse the confirmation) instead of proceeding to render a capped subset and returning ok=true. Equivalently, after the render loop, return false unless `*p == '\0'` (all body consumed). Raising the cap is not sufficient by itself; the guard must refuse rather than approve when the budget is exceeded, matching confirm_constant_power_subpage_take()'s fail-closed contract.
- **confidence**: medium
