# Firmware 7.15 audit handoff

Date: 2026-09-20

Status: **not release-ready**. The 13-PR stack is structurally reviewable and
every adjacent diff is below the 20,000-line limit, but the canonical
python-keepkey integration gate is red on the final stack. Do not merge or
authorize release testing until the blockers in this document are resolved
and the recorded heads are revalidated.

This document is the entry point for a new auditor. It describes the stack,
the intended security boundary, the highest-risk code surfaces, the companion
repositories, current evidence, known failures, and a reproducible review
order. It supplements rather than replaces the focused documents under
`docs/release/audit-units/`, `docs/release/7.15-alpha-delta-audit.md`, and
`docs/security/HANDOFF-ERC7730-ALPHA.md`.

## Non-negotiable release policy

- Metadata signers are loaded at runtime only.
- Runtime signers are session-scoped and require AdvancedMode.
- Disabling AdvancedMode, initializing a new session, authorization loss, or
  workflow teardown must make prior metadata and signer identity unusable.
- No compiled-in KeepKey or alpha trusted root is permitted.
- Runtime metadata is additive: it must not suppress the ordinary/raw review.
- Certified roots, delegate certificates, certified Solana lookup-table
  proofs, certified token definitions, and Portals/dynamic certified decoders
  are excluded from 7.15.
- Regular and bitcoin-only are the only release products.
- python-keepkey remains one canonical multi-release branch. Release-specific
  companion forks are not an acceptable gate mechanism.
- Copilot review has not been requested. It requires explicit human approval.

## Current release blockers

### B1 — final canonical integration suite fails

Run [35543904890](https://github.com/BitHighlander/keepkey-firmware/actions/runs/35543904890)
on final head `6211b7b7ea` passed firmware unit tests, ARM build, dylib tests,
formatting, static analysis, and secret scanning. Its python-keepkey phase
failed: 33 full-suite failures (635 passed, 159 skipped) and eight failures in
the screenshot selection phase (141 passed, 39 skipped, 639 deselected).

Security-relevant failures include:

- runtime signer survives disabling AdvancedMode;
- runtime signer survives session initialization/teardown;
- bytes after an embedded NUL do not change the OLED review;
- Solana verified instruction fields do not all alter the review;
- Solana LUT attestation expectations disagree with the release policy;
- reset/PIN flows disagree with the transactional ceremony implementation;
- authenticator authorization-loss cleanup fails;
- Ethereum off-mainnet native pseudo-address handling fails;
- Osmosis signed-field/canonical-wire assertions fail;
- TON and Omni display-disclosure assertions fail;
- BIP-85 flows and several protection-level expectations fail.

Do not classify these wholesale as stale tests. The two signer-lifetime
failures directly contradict stack 13's claimed invariant, and the NUL/display
failures are transaction-disclosure issues. Triage each failure into one of:
firmware defect, canonical harness defect, explicit excluded capability, or
test isolation defect. Every exclusion must be represented by a precise
capability gate with a positive test on the release where it is enabled.

### B2 — screenshot evidence currently tolerates failed tests

`scripts/emulator/python-keepkey-tests.sh` runs the screenshot pytest phase
with `|| true` and gates only on a nonzero PNG count. A failing test may
therefore leave images that are uploaded as evidence. The full phase still
fails CI, but the screenshot artifact itself must not be interpreted as proof
that its named assertions passed.

The remediation should preserve screenshots and JUnit for diagnosis while
making report certification distinguish passed evidence from frames produced
before a failure or skip. Re-run the exact selector set after correction.

### B3 — version-only gates cannot identify partial 7.15 slices

Stacks 09-13 all report firmware `7.15.0`, while capabilities arrive in later
PRs. A test gated only on `>= 7.15.0` can demand a stack-13 capability from a
stack-09 build. Do not solve this with a release-specific python-keepkey branch
or by weakening final-release assertions. Use an explicit capability contract
for staged CI, defaulting the canonical harness to the complete released
capability set when no partial-stack profile is supplied.

## Security audit map

### Trust establishment and revocation

Start with `signed_metadata.[ch]`, `fsm.c`, storage authorization transitions,
and every `LoadClearsignSigner` call path. Trace key, alias, fingerprint,
metadata cache, and source classification together. Test disable/re-enable,
Initialize, lock, wipe, PIN/passphrase changes, malformed load, full signer
table, and cross-protocol reuse. Zeroing only the key while retaining an alias
or source marker is not sufficient.

### Parser and memory boundaries

Review `pb_decode.c`, transport `.options`, `messages.c`, the response/decode
arenas, tiny-json, ERC-7730 ABI streams, recursive display groups, array/path
arithmetic, embedded calls, and signed-metadata length fields. Check integer
overflow before addition/multiplication, exact terminal consumption, aliasing,
use-after-return, recursion limits, and failure cleanup. Compare emulator and
ARM sizes; host-only success is not evidence of MCU safety.

### What is signed versus what is displayed

For EVM/EIP-712/ERC-7730, Solana, TON, TRON, THOR/Maya, XRP, Hive, EOS,
Osmosis, Bitcoin and Zcash, mutate every signed field independently and prove
that the OLED changes or signing refuses. Pay special attention to embedded
NULs, truncation/paging, token contract versus ticker, chain ID, recipient,
raw amount, fee, calldata tails, array order/dimensions, memos, lookup-table
accounts, and duplicate-output state carried across inputs/outputs.

### Transactional setup and persistent state

For stack 12, prove reset/recovery settings and PIN remain in one zeroized RAM
owner until successful ceremony completion. Exercise cancellation, failure,
Initialize, cross-ceremony messages, stale acknowledgements, repeated entry,
power interruption boundaries, U2F counter preservation, and bitcoin-only
builds. No partially staged value may leak into persistent storage.

### Product and build boundaries

Build regular and bitcoin-only products from clean submodules. Confirm the
regular product contains intended chains, bitcoin-only excludes handlers and
data rather than merely hiding UI, and no obsolete zcash-privacy artifact is
published. Audit dense dispatch-table indexing, linker/arena limits, generated
token byproducts, crypto configuration changes, and release artifact naming.

### Cryptographic and recovery paths

Audit app/boot signature verification for duplicated checks and fault
resistance, canonical Hive signatures and derivation paths, Zcash account
aliasing/export consent, BIP-39 per-word validation, BIP-85 display-only
behavior, and secret/scratch zeroization on every exit.

## Suggested audit order

1. Reproduce B1 on the exact stack-13 and companion SHAs. Preserve JUnit and
   screenshot artifacts before changing code.
2. Resolve signer lifetime and authorization-loss failures first; they guard
   the release trust model.
3. Resolve signed-versus-displayed failures, including the embedded-NUL case.
4. Reconcile excluded Solana certified/LUT behavior with canonical capability
   gates; exclusions must fail closed, not silently skip an available path.
5. Resolve transactional setup/reset failures and re-run interruption cases.
6. Clear the remaining chain and legacy-flow regressions without broad skips.
7. Fix screenshot evidence certification and run the selected and full suites
   from a fresh emulator.
8. Review PRs 01-13 adjacent-diff-first using the audit map above.
9. Rebuild both products, run firmware/board/crypto unit suites, dylib tests,
   canonical python integration, static analysis, formatting, and secret scan.
10. Recheck every PR head/base relationship and changed-line count after any
    restack. Update this document and PR bodies with immutable final SHAs.

## Exit criteria

The handoff is ready for human-authorized audit/testing only when:

- B1-B3 are resolved with focused regression tests;
- all 13 exact PR heads have successful required checks;
- the final canonical full suite has zero unexpected failures and skips;
- screenshot evidence is tied only to passing selected tests;
- regular and bitcoin-only artifacts build from clean recursive submodules;
- all companion gitlinks are canonical and immutable;
- no KeepKey trusted root, persistent signer, or warning-free runtime-provider
  path is present;
- the final heads, artifact digests, test totals, exclusions, and any accepted
  residual risks are recorded here before human authorization.
